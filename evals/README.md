# Экзамен оркестратора — evals

Автоматическая проверка поведения AI-оркестратора (`/api/ai/assist`) на фиксированном наборе кейсов. Запускается против живого dev-сервера с ключом API.

---

## Формат кейса

```js
{
  name: "remove-sms-direct",         // уникальный идентификатор, используется как фильтр
  request: {
    text: "убери смс",               // свободный текст пользователя
    history: [...],                  // (опционально) история сессии; messages: { role, text }
    context: {                       // контекст момента (см. AssistContext в assist-contract.ts)
      screen: "workflow",            // текущий экран
      dataSummary: "...",            // компактная сводка кампаний/сигналов
      graph: { nodes, edges },       // (для workflow-экрана) сводка нод: { id, label, nodeType }
      undoAvailable: true,           // (опционально)
      activeTrigger: { id, label },  // (для trigger-запросов в визарде)
    },
  },
  expect: {
    kinds: ["workflow-ops"],         // ожидаемый массив kind'ов результатов;
                                     // массив массивов = OR: [["clarify"], ["rebuild"]]
    mustContain: ["Ипотека-лето"],   // подстроки, обязанные присутствовать в тексте ответа
    mustNotContain: ["..."],         // подстроки-запреты
    check: (results) => string|null, // кастомная проверка: null = ок, строка = описание провала
  },
  mustPass: true,  // true  — поведенческая гарантия (§7 спеки); провал → exit code 1
                   // false — информационный (считается в счёт, но не ломает exit code)
}
```

### `mustPass`-семантика

`mustPass: true` означает **поведенческую гарантию**: оркестратор обязан пройти этот кейс. Любой провал мастPass-кейса делает `npm run eval` экзит с кодом 1. Это критерий «оркестратор пригоден для демо». Не-mustPass кейсы — дополнительный счёт качества; их провалы не ломают CI (пока).

## Как запускать

### Предусловия

1. **Dev-сервер на порту 3001** с ключом API в `.env.local`:
   ```bash
   npm run dev -- -p 3001
   ```
   Без ключа `GOOGLE_GENERATIVE_AI_API_KEY` сервер вернёт `{"available":false}` и скрипт завершится с exit code 2.

2. **Пауза между кейсами** — по умолчанию 4500 мс (free-tier лимит ~15 req/min). Полный прогон (40 кейсов) занимает ~3–4 минуты.

### Команды

```bash
# Полный прогон
npm run eval

# Один кейс по имени (подстрочный фильтр)
npm run eval -- remove-sms-direct

# Группа кейсов
npm run eval -- stats-

# Другой сервер (например, staging)
EVAL_BASE_URL=http://localhost:3002 npm run eval

# Ускорить (если квота позволяет)
EVAL_DELAY_MS=2000 npm run eval
```

### Exit codes

| Код | Значение |
|-----|----------|
| 0   | Все mustPass прошли |
| 1   | Есть провалы mustPass |
| 2   | Нет ключа / нет сервера |

## Когда запускать — 5 моментов

1. **При разработке AI-слоя (основной цикл).** Провал → правка `afina-knowledge.ts` / `orchestrator-prompt.ts` / схемы инструментов / route handler → точечный перегон фильтром → полный прогон для подтверждения.

2. **Перед коммитом правок AI-файлов.** Если коммит затрагивает `afina-knowledge.ts`, `orchestrator-prompt.ts`, схемы инструментов (`ops-wire-schema.ts`, `stats-patch-schema.ts`, `navigate-schema.ts`, `rebuild-schema.ts`) или `src/app/api/ai/assist/route.ts` — прогнать экзамен, зафиксировать счёт в коммит-сообщении.

3. **Перед демо или коридорным тестом.** Убедиться, что все mustPass зелёные — это минимальный барьер «оркестратор не сломан».

4. **После коридорного теста.** Превратить интересные фразы пользователей из журнала aiLog в новые кейсы (см. «Как добавлять кейсы»), добавить в `cases.mjs`, прогнать.

5. **При смене модели (`AFINA_AI_MODEL`).** Новая модель может давать другой тон, другую выборку инструментов. Полный прогон покажет регрессии до того, как пользователи увидят их.

## Как добавлять кейсы из журнала aiLog

Журнал (`«Журнал AI» в дев-панели → «Выгрузить журнал»`) — главный источник новых кейсов. Кандидаты:

- **`outcome: "fallback"`** — оркестратор не смог обработать запрос, ушёл в офлайн-ответ. Если запрос должен был пройти — добавить mustPass-кейс.
- **`outcome: "applied"` с неверными `applied`** — AI применил что-то, но неправильное. Добавить кейс с `check` и `mustNotContain`.
- **Повторяющиеся фразы** — если одна и та же формулировка встречается несколько раз с плохим исходом — высокоприоритетный кейс.

Чтобы добавить кейс:

1. Взять `text` из журнала, подобрать `context` (screen + dataSummary из реального состояния или из стандартных контекстов `workflowCtx` / `statsCtx` / `wizardCtx`).
2. Запустить один раз с ключом, посмотреть что вернул оркестратор.
3. Написать `expect` — зафиксировать правильное поведение.
4. Поставить `mustPass: true` если это поведенческая гарантия.

## Почему НЕ в CI

- **Ключ API.** Реальный `GOOGLE_GENERATIVE_AI_API_KEY` не должен попадать в CI-секреты прототипа.
- **Квота.** Free tier: ~15 req/min, ~1500 req/day. 40 кейсов × 4.5 сек = ~3–4 мин — допустимо вручную, но в CI блокирует пайплайн при параллельных запусках.
- **Недетерминированность.** LLM-ответы не стабильны. Флапающий тест в CI — хуже, чем его отсутствие.
- **Длина прогона.** ~3–4 минуты на весь набор — слишком долго для pre-push hook.

Правило: экзамен гоняет разработчик вручную в моменты 1–5 выше; CI (если появится) гоняет только юнит-тесты (`npm test`).
